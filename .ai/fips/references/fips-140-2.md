# FIPS 140-2 Reference Index

Created: 2026-06-10

Purpose: foundation reference set for comparison analysis between FIPS 140-2 and FIPS 140-3, with emphasis on requirements that may affect Keycloak, Java security providers, TLS, key management, and approved algorithm selection.

## Source Policy

Only official NIST, CSRC, or NVLpubs government-hosted sources are indexed here. FIPS 140-2 is superseded by FIPS 140-3, but its standard, annexes, derived test requirements, and implementation guidance remain useful for comparison and for understanding older CMVP validation language.

## How To Use This Index

Start with the FIPS 140-2 standard, then the four annexes:

- Annex A is the older approved security function reference point.
- Annex B covers approved protection profiles.
- Annex C covers approved random number generators.
- Annex D covers approved key establishment techniques.
- The DTR maps requirements to validation evidence and test expectations.
- The Implementation Guidance contains CMVP clarifications and program guidance.

For comparison with FIPS 140-3, focus on how the FIPS 140-2 annex structure maps into SP 800-140C, SP 800-140D, SP 800-140E, and the FIPS 140-3 IG. For Keycloak and Java provider research, pair Annex A, Annex C, Annex D, and the IG with SP 800-52 Rev. 2 for TLS, SP 800-131A Rev. 2 for algorithm/key-size transitions, SP 800-57 for security strengths, SP 800-90 series for entropy/DRBG behavior, and SP 800-38 series for AES modes.

## Citation Requirement For Algorithm Inventory

When assembling supported ciphers, cipher suites, encryption algorithms, signatures, MACs, KDFs, random number generators, or key establishment mechanisms, every row must include:

- The exact algorithm or suite name as observed in Keycloak, Java, JSSE, or Bouncy Castle.
- The official NIST/CSRC document that mentions or governs it.
- The section, annex item, table, or implementation guidance paragraph where it is mentioned.
- A local text citation pointing at the extracted `.txt` file and line number where practical.
- A short status note such as `approved`, `allowed with restrictions`, `deprecated`, `disallowed`, `non-approved`, or `needs confirmation`.

Do not rely on algorithm names alone. For example, `AES/GCM/NoPadding` should cite both an observed provider name and the governing NIST text, such as FIPS 140-2 Annex A plus SP 800-38D; a TLS suite should cite SP 800-52 Rev. 2 and the precise table or paragraph covering that suite.

## Comparison Notes

- FIPS 140-2 placed approved algorithms and mechanisms in Annex A through Annex D. FIPS 140-3 moves this structure into SP 800-140C, SP 800-140D, SP 800-140E, and related IG.
- SP 800-67 Rev. 2 is included only for historical FIPS 140-2/TDEA comparison. The NIST PDF marks it withdrawn as of January 1, 2024, so it should not be treated as a current FIPS 140-3 implementation target.
- SP 800-52 Rev. 2 should be used when comparing TLS protocol and cipher suite implications rather than relying only on the general FIPS 140-2 Annex A list.
